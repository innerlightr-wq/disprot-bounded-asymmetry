# Results

Everything in `tables/`, `diagnostics/` and `figures/` is regenerated by
`python run_all.py` from `data/raw`. Nothing here is hand-edited.

`deposited_originals/` is the exception: it holds archival copies from the
published Zenodo record, is never written by the pipeline, and **must not be
edited or overwritten**. See §4.

## 4. `deposited_originals/` — archival copies, not pipeline output

Three CSVs in the published Zenodo deposit **cannot be produced by any script in
that deposit.** They have richer schemas, written by code that was not archived
alongside them, and they use CRLF line endings while every script output uses
LF.

They are preserved here unchanged, with a `_deposited` suffix, because they are
part of the historical record. The corresponding files in `diagnostics/` are
what the archived code actually reproduces. Both are kept so the difference is
visible rather than resolved by silently overwriting one with the other.

**Do not edit, overwrite or regenerate anything in `deposited_originals/`.**

### Schema differences

| File | Columns in `deposited_originals/` | Columns in `diagnostics/` | Difference |
|---|---|---|---|
| `source_file_audit` | `group`, `filename`, `bytes`, `md5`, `sha256`, `records`, `size_field`, `ncbi_taxon_id`, `organism`, `unique_acc`, `unique_disprot_id`, `release`, `variant` | `file`, `bytes`, `md5`, `n_records`, `n_unique_acc`, `organism`, `ncbi_taxon_id` | Deposited version adds `group`, `sha256`, `size_field`, `unique_disprot_id`, `release`, `variant`; column names differ (`filename`/`file`, `records`/`n_records`, `unique_acc`/`n_unique_acc`). **All values present in both agree.** The SHA-256 values in the deposited file were independently confirmed against the input files and are reproduced in `../data/metadata/source_queries.csv`. |
| `sign_stability` | `feature`, `comparison`, then `B[…]` and `A[…]` for each of the nine specifications, then per-specification stability flags | `feature`, `group_A`, `group_B`, `n_specs`, `n_pos`, `n_neg`, `sign_stable` | Deposited version is a **wide** per-specification table of every B̄ and Ā value; the script emits a **narrow** count summary. The underlying per-specification values are all present in `diagnostics/robustness_sensitivity.csv`, and the counts agree: 7 of 12 comparisons sign-stable in both. |
| `gap_by_taxon_tests` | `group_a`, `group_b`, `n_a`, `n_b`, `median_gap_a`, `median_gap_b`, `mannwhitney_U`, `mannwhitney_p`, `rank_biserial`, `ks_stat`, `ks_p`, `significant_at_0p05` | `group_A`, `group_B`, `median_gap_A`, `median_gap_B`, `mw_p`, `rank_biserial` | Deposited version adds group sizes, the U statistic, a KS test and a significance flag. It also carries **small numeric differences** — see below. |

Rank-biserial effect sizes agree to five decimal places or better (largest
difference 1.7×10⁻⁵, human vs bacterial). Median gaps agree exactly; the
deposited file simply rounds to six decimals.

The pattern — differences only in the two comparisons with the largest sample
imbalance, always in the same direction — is consistent with a difference in tie
or continuity handling in the unarchived code. The exact cause was **not**
determined, and no attempt was made to reverse-engineer the missing code or to
tune the surviving script to match. Claiming exact reproduction of these three
files would be false.

### What this does and does not affect

**No manuscript conclusion or reported threshold changes.** The manuscript
states, for the taxon-dependence of the signed gap, that Mann–Whitney
*p* ≤ 5×10⁻³ for the five significant pairs, *p* < 10⁻⁴ for human vs bacterial,
and *p* = 0.56 for the null human vs nematode comparison. Every one of those
holds under both versions, with wide margin. The abstract's *p* < 10⁻⁴ claim
holds under both. No index, confidence interval, correlation or figure in the
manuscript is computed from any of these three files.

**All manuscript-critical results reproduce.** Table 2 in full, the §3.2
concordance statistics, the §3.4 sensitivity analysis and all five figures come
from `thales_curated_sample_results.csv`,
`cross_taxon_calibration_summary.csv`, `robustness_sensitivity.csv` and
`asymmetry_profiles.npz` — all of which are byte-identical between the archived
deposit and a fresh run of this repository.

**Row-order differences have a diagnosed cause.** The deposited tables are
ordered Bacterial-first, and their `source_file` column shows the *E. coli*
export was the unsuffixed download in the generating session. The original
`01_build_tables.py` discovered inputs with `sorted(glob.glob("*.json"))`, so
row order tracked arbitrary browser suffixes. This affected no computed value:
group membership derives from `ncbi_taxon_id`, and within-group ordering comes
from each file's internal record order, which is why the bootstrap CIs
reproduced to the last digit despite the reordering. The refactor replaces the
glob with an explicit ordered manifest, fixing row order to the group order of
manuscript Table 1.

**Not present in the deposit, so not comparable:** all 14 figure files,
`dphi_operator_test.csv`, `group_feature_summary.csv`,
`phase1_integrity_checks.csv` and `asymmetry_profiles.npz`. These are generated
successfully and are confirmed to be built from data that is byte-identical to
the deposit, but there is no archived copy to compare them against, so
reproduction of the *published figure files themselves* is verified only
indirectly. If bit-level figure provenance matters for the submission, add the
current `figures/` directory to the next deposit.

## 6. Incidental finding: the human n = 1,246 vs 1,247 off-by-one

The manuscript reports 92 human proteins lacking an AlphaFold value in Table 1
(implying 1,247 usable) but n = 1,246 for the human Spearman concordance in
§3.2. Both numbers are correct; they are computed on two different definitions,
and the pipeline output identifies the single record responsible.

**Accession `P09651-2`** (human, isoform, 320 residues) carries the literal
**string `"NaN"`** in its `alphafold_very_low_content` field rather than a
number or JSON `null`.

- `01_build_tables.py` sets `af_available = (af is not None)`. The string
  `"NaN"` is not `None`, so this record counts as *present* → **92 missing**,
  which is Table 1's figure and Figure 1's annotation.
- `pd.to_numeric(..., errors="coerce")` converts `"NaN"` to a float NaN, so the
  record is dropped by `dropna` in the concordance analysis → **1,246 paired**,
  which is §3.2's figure.

Both counts are internally consistent with their own definition, and no
statistic is wrong: the record has no usable value under either reading. But the
manuscript does not explain the one-unit difference, and a referee comparing
Table 1 against §3.2 will notice it.

This is the same class of defect as the documented 34 string-typed values (see
caveat "Mixed data types" in `../data/README.md`) — the export is inconsistently
typed, and `"NaN"` is a string that survives a null check while failing a
numeric one.

**Suggested manuscript fix, at the author's discretion** — no code change is
required, and none was made:

> Report the count of proteins with a *numerically usable* value rather than a
> non-null one (93 human, 1,246 usable), or add a footnote to Table 1 noting
> that one further human record carries a non-numeric placeholder and is
> excluded from the concordance analysis.

Adopting either wording would make Table 1 and §3.2 agree. Changing
`af_available` to test numeric usability instead would alter the published
Table 1 value from 92 to 93, so it was **not** done here.
